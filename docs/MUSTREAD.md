# Must Read 쓰는 법 (Biz.Brief · All.Brief)

이 문서는 브리프를 쓰는 Claude 세션이 따르는 지침입니다. 하루 두 번 예약 작업이 전용 세션을 깨우면,
그 세션이 이 문서대로 **두 편**을 써서 저장소에 올립니다. API 키는 쓰지 않습니다.

| 글 | 무엇 | 저장 파일 |
| --- | --- | --- |
| **Biz.Brief** | 사업 아이템·돈 버는 방법 (해외 아이템, 따라하기, AI 사업, 국내 창업, 부업) | `public/data/bizbrief-<판>.json` |
| **All.Brief** | 일반 뉴스 (정치, 사회, 국제, 과학·기술, 생활·문화) | `public/data/allbrief-<판>.json` |

- 아침판: 한국 시간 06:41 · 저녁판: 18:41
- 두 편은 다루는 영역이 겹치지 않게 씁니다. **두 편 모두 주가·지수·종목·투자 판단을 넣지 않습니다.**
  같은 사건이 둘 다에 걸치면 Biz는 그것이 만드는 사업 기회·위험을, All은 사건 자체와 사회적 의미를 씁니다.

## 순서

1. 최신 `main`을 받습니다 (`git pull --rebase origin main`). 06:30·18:30 GitHub Action이 `public/data/feed.json`을 갱신합니다.
   GitHub 예약 실행은 늦거나 빠질 때가 있습니다. 피드가 갱신되지 않았어도 **기다리지 말고** 바로 쓰세요.
   그때는 기사 목록이 오래됐으니 웹 검색 비중을 높여 오늘 소식을 직접 찾습니다.
2. **Biz.Brief**
   1. `node scripts/mustread-context.mjs <morning|evening>` — 첫 줄이 ALREADY_DONE이면 Biz는 건너뜁니다.
   2. 기사 목록을 출발점으로 **웹 검색과 웹 페이지 읽기로** 사실과 숫자를 확인합니다.
   3. 아래 Biz 구조로 마크다운 파일 하나에 씁니다 (저장소 밖 임시 경로).
   4. `node scripts/save-mustread.mjs <판> <파일>` — 검사에 걸리면 고쳐서 다시 저장합니다.
3. **All.Brief**
   1. `node scripts/mustread-context.mjs <판> all` — 첫 줄이 ALREADY_DONE이면 All은 건너뜁니다.
   2. 주요 일간지 헤드라인 목록을 출발점으로, 여러 신문이 함께 크게 다룬 사안을 고르고 웹 검색으로 확인합니다.
   3. 아래 All 구조로 씁니다.
   4. `node scripts/save-mustread.mjs <판> <파일> all`
4. 새로 저장한 json 파일만(한 개 또는 두 개) 커밋해 `main`에 올립니다.
   커밋 메시지: `Must Read (<판>) <YYYY-MM-DD>` (All만 있으면 `All.Brief (<판>) <YYYY-MM-DD>`).
   푸시가 거절되면 `git pull --rebase` 후 다시 올립니다.

## 쓰는 원칙

- **숫자**(지수, 등락률, 지표, 금액)는 이번에 검색하거나 읽은 페이지에서 확인한 것만 씁니다.
  확인하지 못한 숫자는 쓰지 않고, 필요하면 "확인하지 못했다"고 적습니다.
- **사실과 해석을 구분합니다.** 해석은 `**해석:**` 또는 `**제 판단:**`으로 시작하는 문단에만 씁니다.
- **출처**: 항목마다 끝에 `출처: [매체 – 기사 제목](https://...)`. 주소는 이번에 실제로 검색 결과로 보았거나
  열어 본 페이지, 또는 컨텍스트의 기사 목록에 있는 주소만 씁니다. 주소를 짐작해서 만들지 않습니다.
- **투자 권유를 하지 않습니다.** 주식·코인·부동산 매매를 권하지 않고, 사업 아이템도 "성공 보장"처럼 쓰지 않습니다.
- 자극적인 표현, 과장, 공포를 부추기는 말을 쓰지 않습니다. 차분하고 명료한 한국어 평서문.
- 분량은 Biz 6,000~9,000자, 항목 7~10개 (All은 아래). 마크다운만 씁니다 (HTML 태그 금지 — 앱이 글자로 보여줍니다).
- 표는 비교할 때만. 표 첫 열은 짧은 이름(아이템·지표)으로 둡니다.

## Biz.Brief 원칙

Biz.Brief는 **돈을 버는 사업과 일**의 이야기입니다. 주가·지수·종목·코인 매매, 금리 전망 같은 투자 이야기는 쓰지 않습니다.
(기업이 투자를 유치했다는 소식은 "그 사업이 어떻게 돈을 버는가"를 설명할 때만 씁니다.)

- 다룰 것: 해외에서 뜬 사업 아이템, 기발한 서비스·제품, 다른 나라 모델의 한국 적용(따라하기), AI로 만드는 사업·1인 사업·자동화,
  국내 창업·스타트업의 새 모델, 부업·사이드 프로젝트, 정부 창업 지원사업과 규제 변화.
- 아이템마다 **무엇을 파는가 → 누가 사는가 → 어떻게 돈을 버는가(수익 모델) → 확인된 숫자 → 한국에서 하면**의 순서로 씁니다.
- **매출·수익 숫자는 출처를 붙이고, 창업자 본인 주장이면 "본인 공개 기준"이라고 밝힙니다.** 확인이 안 되면 쓰지 않습니다.
- "월 1,000만 원 보장", "누구나 쉽게" 같은 과장은 쓰지 않습니다. 실패 사례와 위험(초기 비용, 규제, 경쟁)도 함께 적습니다.
- 다단계, 도박성, 불법 소지가 있는 아이템(무허가 영업, 저작권 침해, 개인정보 판매 등)은 소개하지 않습니다.
  한국 적용을 쓸 때 인허가·규제가 걸리면 그 점을 분명히 적습니다.
- 출처: 컨텍스트의 기사 목록(해외 사업 아이템·국내 창업·AI·한국 산업)을 출발점으로, 웹 검색으로 사실과 숫자를 확인합니다.
  RSS가 없는 Springwise·Trend Hunter·Exploding Topics·Indie Hackers·Starter Story는 웹 검색으로 찾아 볼 수 있습니다.
- 분량은 한국어 6,000~9,000자.

### 오늘의 아이템 (가장 중요한 칸)

독자가 가장 좋아하는 칸입니다. **작고 기발한 돈벌이 아이템을 짧은 카드로 10~14개** 모읍니다.
이 칸은 앱의 Biz.News 맨 위에 카드로 그대로 뜨므로 형식을 지킵니다.

```
## 오늘의 아이템
- **[분류] 아이템 이름** 무엇인지 한두 문장(누가, 무엇을, 얼마에). 왜 돈이 되는지·어디에 적용할지 한 문장. [매체 – 기사 제목](https://...)
```

- 한 줄 = 한 아이템. 줄 안에서 줄바꿈하지 않습니다. 아이템마다 출처 링크 하나.
- 분류는 다음 중 하나: `로컬·오프라인` `온라인·구독` `AI·도구` `해외 따라하기` `콘텐츠·크리에이터` `제조·커머스` `지원사업`.
  한 판에 최소 4가지 분류가 섞이게 고릅니다.
- 고르는 기준: 1인~소규모로 시작할 수 있고, '왜 사람들이 돈을 내는지'가 한 문장으로 설명되는 것.
  거대 투자 유치·대기업 소식은 이 칸에 넣지 않습니다(아래 섹션에서 다룹니다).
- 좋은 예:
  - 지역 특산물 + 익숙한 외식 메뉴(당진 쌀·서해 수산물 초밥집)
  - 무료가 당연한 분야의 유료 버전(광고 없는 이메일 연 99달러)
  - 인기 AI 도구와 기존 도구를 잇는 작은 연결 앱(Claude Code로 피그마 수정)
- 소재 찾는 곳: Product Hunt·Show HN·GeekNews Show GN(작은 제품), 스타트업엔·플래텀·벤처스퀘어(국내 소상공인·로컬 창업),
  Entrepreneur·Inc.(작은 브랜드 사례), Starter Story·My First Million·Startup Ideas(아이디어 팟캐스트 소개글),
  Modern Retail(소규모 브랜드 전술), Side Hustle School(매일 부업 사례 하나). 웹 검색으로 Springwise·Trend Hunter·Indie Hackers,
  국내는 기업마당·K-Startup 지원사업 공고와 와디즈·텀블벅 인기 펀딩도 찾아봅니다.

## All.Brief 구조 (아침·저녁 공통)

분야마다 2~3개, 전체 항목 7~10개. 분량은 한국어 5,000~8,000자.

```
# 🗞 All Brief — 아침   (저녁판은 "All Brief — 저녁")

(날짜 줄)

- **정치** 한 줄

## 2. 사회
## 3. 국제
## 4. 과학·기술   (AI는 산업·투자 얘기 말고 사회적 영향 위주)
```

## 바꾸고 싶을 때

독자 소개와 관심사는 `sources.json`의 `profile`에서, 소스는 `sources.json`의 `sources`에서, 글의 구조와 원칙은 이 문서에서 고칩니다.
다음 실행부터 반영됩니다.
